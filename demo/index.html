Reviewer guide · implementation explained

How CrewForge is designed to stay correct

READ THIS BEFORE JUDGING

The interactive board above is a deliberately backend-free product demonstration. This section explains the separate full-stack implementation in the repository and links directly to its code, tests and benchmark evidence. It is written to make the engineering decisions reviewable without implying that the public static page is processing real participants.

Deployment boundary: This URL serves a static HTML/CSS/JavaScript demo. Create, join, leave, reset and matching actions change only this browser's local storage. There are no accounts, shared database, invite emails, server-side membership writes or live multi-user updates on this URL. The full-stack Next.js + MongoDB application is source-controlled and tested in CI, but is not deployed as a public backend.
The hard problem

One last seat. Fifty simultaneous requests.

A browser-side “seats remaining” check is not a concurrency control. If 50 clients read one available seat before any write commits, all 50 can believe they are eligible. CrewForge makes the database decide who wins.

Authenticate + validate

The route verifies the session, validates the team and hackathon identifiers, checks request origin and validates the idempotency key.

Reserve conditionally

Inside a MongoDB transaction, update the team only when it is open and its authoritative memberCount is still below maxSize.

Insert membership

Insert the participant membership in the same transaction. A unique compound index on (hackathonId, userId) blocks a second team membership.

Write audit event

The membership change and its audit record commit together. A failed capacity check or uniqueness constraint aborts the transaction.

Retry transient conflicts

MongoDB driver transaction retries handle transient write conflicts. A repeated idempotency key for the same action returns the logical prior result.

Exactly one winner

The integration test starts 50 contenders for one remaining seat and asserts one successful join, correct memberCount and no duplicate side effects.

BEGIN TRANSACTION
UPDATE teams
SET memberCount = memberCount + 1
WHERE _id = teamId AND status = 'open' AND memberCount < maxSize
REQUIRE exactly one team row matched
INSERT memberships (hackathonId, userId, teamId)
-- unique (hackathonId, userId)
INSERT idempotency record
INSERT audit event
COMMIT

Any failed invariant → ABORT (no partial seat reservation)

The actual test calls the same joinTeamTransaction helper used by the HTTP route; it is not a separate toy implementation. Inspect the 50-contender integration test and the team transaction code.

Engineering decisions

Trade-offs and remaining production work

MongoDB transactions + unique indexes

Correctness lives at the source of truth and holds across multiple app instances. Trade-off: replica-set infrastructure, transaction overhead and connection-pool discipline.

SSE instead of WebSockets

The board needs server-to-client invalidation, not bidirectional messaging. SSE is simpler and reconnects naturally; long-lived connections and change-stream resource use still need hosting-specific validation.

Explicit demo boundary

A static demo is easy for judges to open and requires no credentials. It does not pretend to prove multi-user behavior; that proof is supplied by reproducible database tests.

Known challenge gaps: pending join requests with leader accept/decline, leader-driven member removal, optimistic rollback against server conflicts, Docker Compose, tracing/metrics and a chaos test are not implemented. The full-stack service also has no public backend deployment. Before claiming full challenge completion, implement those flows, add targeted tests, deploy against a replica-set database and verified email sender, run the staging authorization/invite/realtime/failure matrix, benchmark the deployed region, and add operational alerts plus backup/restore and rollback rehearsal. The static demo deployment does not satisfy the deployed-backend requirement.
What would be done with one more engineering week?

First, deploy a staging backend with production-like MongoDB and email configuration. Second, automate the outstanding invite lifecycle, leader authorization, origin/rate-limit, SSE multi-session and failure-mode tests. Third, run a 15–30 minute soak and burst test against the deployed region, capture p50/p95/p99 and database pool metrics, and set an explicit capacity limit. Finally, add tracing/metrics, alerting, backup-restore rehearsal and a controlled server-kill-during-join chaos test. Docker Compose is also a useful local reviewer path, but it is secondary to deployed correctness evidence.
